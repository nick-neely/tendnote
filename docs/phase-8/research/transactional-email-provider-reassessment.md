# Transactional email provider reassessment

Research for the Phase Eight Household Invitation implementation decision, 2026-08-08. This reassesses, rather than silently replaces, the earlier Resend default in [household invitation delivery and abuse constraints](household-invitation-delivery-and-abuse-constraints.md). Prices and beta status are time-sensitive.

## Decision summary

Keep the Tendnote-owned transactional-email adapter and the current **Resend default** for now. Resend remains the lowest-friction production choice for Phase Eight: its free tier covers 3,000 emails/month (100/day), it has direct REST and SMTP sending, explicit 24-hour request idempotency, signed HTTP webhooks, automatic suppression, and a straightforward Next.js/Vercel integration ([pricing](https://resend.com/pricing?product=transactional), [idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [webhooks](https://resend.com/docs/webhooks/introduction)).

**Cloudflare Email Sending is now the only alternative that merits a short, deliberate proof before the invitation ticket is implemented.** It is compelling because Tendnote's domains already use Cloudflare DNS and, if the account already has Workers Paid, includes 3,000 sends/month and then costs $0.35/1,000. It offers REST from any platform, a Workers binding, SMTP, managed SPF/DKIM/DMARC records, lifecycle events, and suppression ([sending](https://developers.cloudflare.com/email-service/get-started/send-emails/), [pricing](https://developers.cloudflare.com/email-service/platform/pricing/), [authentication](https://developers.cloudflare.com/email-service/concepts/email-authentication/), [events](https://developers.cloudflare.com/email-service/platform/event-subscriptions/)).

But it is a **public beta announced 2026-04-16**, and SMTP only entered beta on 2026-06-08 ([announcement](https://developers.cloudflare.com/changelog/post/2026-04-16-email-sending-public-beta/), [SMTP announcement](https://developers.cloudflare.com/changelog/product/email-service/)). Tendnote currently deploys to Vercel, so it would use Cloudflare's REST API—not a native Worker binding—and receive events through Cloudflare event subscriptions/Queues rather than a provider's ordinary direct HTTP webhook. The reviewed Cloudflare sending documentation does not document a provider request-idempotency facility. Those are acceptable risks only after a focused production-like proof; they are not reasons to make Cloudflare a default merely because it hosts DNS.

Do **not** select Postmark, Mailgun, SendGrid, Mailtrap, or SES for this low-volume launch unless a separate constraint changes (existing account, compliance, AWS standardization, or materially higher volume). They all provide viable transactional delivery, but none improves on the Resend/Cloudflare decision enough to justify its cost or operational surface.

## Non-negotiable Tendnote contract

Provider choice must remain an adapter detail. A `Household Invitation` owns its capability, expiry, terminal state, and durable delivery attempt; an explicit Owner action creates an attempt, and a background dispatcher claims it before calling the provider. The provider adapter accepts the immutable attempt id, recipient, template payload, and canonical acceptance URL and returns a provider message id or typed failure.

The database attempt/claim remains the exact-once authority. Reuse the same attempt id for ambiguous retries, never for an explicit resend (which rotates the invitation secret and creates a new attempt). Use a provider idempotency key where available, but no provider's retention window substitutes for Tendnote's durable lease. In the reviewed provider material, Resend is the only candidate with a documented reusable send-idempotency key; it deduplicates for 24 hours ([Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys)).

Persist the minimum operational state required for `accepted`, `delivered`, `deferred`, `bounced`, `complained`, `failed`, and `suppressed`; verify, deduplicate, and order events before changing it. A provider dashboard is not Tendnote's audit log. Do not enable open/click tracking for capability links, record the full link/token or message body, reveal suppression/account information to an Owner, or send invitations other than through an explicit Owner action.

Every candidate requires a dedicated transactional subdomain or return path, authenticated SPF and DKIM, an aligned DMARC policy, and a monitored Reply-To. Provider-managed DNS is a convenience; it does not eliminate the product's email-authentication and abuse obligations.

## Cloudflare proof gate

Before changing the default, use a non-production Cloudflare Email Sending domain/subdomain and a narrow disposable adapter to prove all of the following:

1. An explicit Vercel-hosted server call can send a single plain-text-plus-HTML invitation through the REST API using a least-privilege secret; no Worker migration is required.
2. Cloudflare-managed SPF/DKIM plus an aligned DMARC record validate and deliver to Gmail, Outlook, iCloud, and a custom-domain mailbox. Inspect headers, not only inbox arrival.
3. The event subscription reaches a controlled consumer; it correlates every required terminal state with the provider message id, safely ignores duplicate/replayed `eventId` values, and treats out-of-order state monotonically.
4. Hard bounce, complaint, and provider suppression produce the expected neutral Tendnote delivery state; a suppressed send must not consume or reactivate the invitation.
5. An intentionally ambiguous network failure does not result in duplicate email. Since no Cloudflare request-idempotency guarantee was found in the reviewed sending docs, prove Tendnote's durable attempt claim prevents a second provider call.
6. Cloudflare's current public-beta support, quota behavior, and event-subscription retention/replay expectations are acceptable to the operator.

If that gate passes, Cloudflare is a reasonable Phase Eight selection, particularly if Workers Paid is already a sunk cost. If it does not, ship the provider-neutral Resend adapter and re-evaluate Cloudflare after its Email Sending API and event-delivery semantics are generally available/stable.

## Explicitly not a decision

This research does not authorize opening a provider account, changing DNS, creating API keys, sending test email to real recipients, or changing `docs/prd.md`. The final selection belongs in the implementation decision for **Send and accept verified Household Invitations**; it should append this evidence and record the selected provider plus the operational ownership of its DNS, secrets, webhook/event consumer, and production readiness evidence.
