# Tendnote route, data, and mutation inventory

Status: evidence for [Inventory Tendnote’s route data and mutation consistency seams](https://github.com/nick-neely/tendnote/issues/288), captured July 23, 2026 at commit `6a1ca19`.

## Executive read

Tendnote currently has one request-bound authenticated rendering model and several distinct consistency models layered on top of it.

- Every admitted product page exports `dynamic = "force-dynamic"` and resolves a Better Auth session plus Private Beta Access before loading product data. No authenticated page is currently a reusable static shell.
- The shared `AppShell` is a client component mounted by every admitted product page. It owns desktop and mobile navigation, Search, Capture, Today handlers, reminder reconciliation, PWA registration, and offline state. That makes it both the strongest reusable-shell candidate and a source of client-code and server-action coupling on otherwise light routes.
- Page reads are owner- or caller-scoped. Household-visible Actions, Assets, Saved Items, and their child records still apply per-record visibility; owner-only review state must never be shared with household members.
- Same-surface interaction state is usually updated from the successful server-action result and then reconciled with `router.refresh()`. Review, destructive, provider, external-draft, import, and upload flows wait for server confirmation.
- Invalidation is path-based and narrow. It is not yet a complete dependency graph: several mutations affect Today, Review, linked Assets, or another route while invalidating only their owning page. Global Capture invalidates `/review` and `/today`, although the live Today/Review page is `/` with Review selected by `?tab=review`.
- Route payloads cross the React Server Component boundary as explicit view models, typed result unions, dates converted to strings where clients need them, and bounded lists. Any cache boundary must preserve those projections instead of exposing database rows or relying on a client-supplied owner id.

This is an inventory, not a Cache/Stream/Block decision. It identifies the seams the later route, shell, partial-prefetch, and optimistic-interaction tickets must decide.

## Shared authentication and shell seams

| Seam | Current behavior | Constraint for the upgrade |
| --- | --- | --- |
| Page admission | `requireAdmittedOwner()` reads request headers, resolves the Better Auth session, evaluates Private Beta Access, and redirects unauthenticated or pending callers. | Session, admission, and owner resolution remain request-bound. Never put their result in a shared cache. |
| Server actions | `requireAdmittedOwnerForAction()` repeats the trusted access check and throws for stale, unauthenticated, or pending clients. | A serialized `ownerUserId` is presentation context, not authority. Every mutation and sensitive read action must resolve the caller again on the server. |
| Local development | Account and reminder deep-link routes can use the explicit non-production fallback owner. Ordinary admitted pages use the same fallback through `requireAdmittedOwner()`. | A new shell must preserve production fail-closed behavior and keep the fallback unreachable in production. |
| Shared shell | `AppShell` receives `ownerUserId` and optional Today/Eve data, then mounts desktop nav, mobile nav and flows, PWA registration, reminder time-zone reconciliation, standalone reminder continuation, and offline state. | Static shell extraction should separate cacheable layout/navigation from owner-bound props and optional route data. Do not make every route pay for Today/Eve data or privileged server-action imports merely because it uses navigation. |
| Navigation | Desktop exposes Today, People, Actions, Assets, Saved Items, and Account. Mobile exposes Today and Review directly, Search/Capture as overlays, and the remaining destinations through Menu. | Route-shell and prefetch policy must distinguish always-visible high-probability links from the mobile Menu fan-out measured in the navigation baseline. |
| Review | Review is not a separate route. It is the dashboard page at `/?tab=review`, with the same server read fan-out as Today. | Cache keys, invalidation, tests, and route naming must treat Today and Review as views of `/`, not `/today` and `/review`. |
| Search and Capture | Search and Capture are full-screen mobile flows inside `AppShell`, not pages. Search calls an owner-gated read action. Capture calls owner-gated mutation actions and can add a person, schedule a reminder, change an outcome, or undo it. | They need immediate overlay feedback without forcing a route navigation. Their server actions still require authoritative owner resolution and cross-route reconciliation. |
| Eve | The dashboard supplies the live `AssistantPanel`; other routes mount the shell without the Eve panel. A local composer draft is keyed by owner and surface in `localStorage`. | Never cache or serialize conversation state into a shared shell. Preserve owner-keyed local draft isolation and explicit approval gates for Eve-backed writes. |

The pending-access and authentication pages are request-dynamic access boundaries, not admitted product surfaces. They still must remain correct through the framework upgrade, but the map explicitly deprioritizes aggressive optimization of sign-in, sign-up, password recovery, and uncommon deep links.

## Mutation authority and feedback classes

| Class | Current examples | Required invariant |
| --- | --- | --- |
| Deterministic, reversible local-domain lifecycle | Complete/reopen/dismiss/defer an Action or follow-up; archive/restore an Asset or Saved Item; edit an Area; Today Later/Not today. | Immediate pending/acknowledgement is safe. The successful server result remains authoritative, failures leave or restore the prior UI, and a later server render must reconcile without resurrecting resolved rows. |
| Deterministic create/edit | Create or edit a person-bound follow-up, Action, Asset, Saved Item, visibility, links, or reminder schedule. | Do not invent an id or claim success before validation. Insert/update the returned view immediately after success, then reconcile server-derived counts, audiences, links, and Today eligibility. |
| Review-gated AI or imported outcome | Suggested memories, follow-ups, Actions, Asset groups/memories/links, unresolved person mentions, Calendar suggestions, Contact import candidates. | A proposal is not domain truth. Accept/edit/dismiss must be server-confirmed, owner-authorized, and reflected in both Review and the destination domain surface. |
| External effect or provider state | Google/Discord connect or disconnect, Discord delivery configuration, Gmail draft creation/update, contact preview fetch/import, evidence upload. | Keep explicit user intent and server/provider confirmation. Never present an external draft, send, import, upload, or capability change as complete based only on local optimism. |
| Destructive | Permanent person deletion, permanent Asset deletion, unique Saved Item source deletion, connection revocation. | Preserve the current proportional confirmation and impact preview. Wait for server success; then navigate or remove the row and invalidate every affected view. |
| Read-only transient | Search, Asset browse/search, Calendar preview, history dialogs, deletion-impact query, reminder deep-link resolution. | These may stream or cache only inside the caller's visibility boundary. They must not mutate merely because they were prefetched. |

## Current invalidation and refresh inventory

There are no `revalidateTag` calls in the Web app today. Reconciliation is a combination of server-action return values, client list state, `router.refresh()`, and `revalidatePath`.

| Mutation family | Current `revalidatePath` coverage | Cross-route consumers to account for before caching |
| --- | --- | --- |
| Today shortlist | `/` | The underlying follow-up or Action also appears on person detail, Actions, Action Today, Asset detail, Search, and reminders. |
| Briefs | `/`; accepted brief follow-up also person detail | Follow-up state can affect Today and person detail; the explicit extra person invalidation covers the acceptance destination. |
| Suggested general Actions | `/actions`, `/` | Accepted Actions may also appear in Action Today, linked Asset detail, Search, and reminders. |
| Suggested follow-ups | Person detail; Calendar suggestions also `/` | Non-Calendar review actions do not explicitly invalidate `/`, even though the dashboard Review Queue and Today can consume them. |
| Ordinary follow-ups | Person detail only | Dashboard follow-ups, Today, Search, and reminders also consume follow-up state. |
| Ordinary Actions and Areas | `/actions` | `/`, `/actions/today`, linked Asset detail, Saved Item promotion results, Search, and reminders may consume the same state. |
| Asset-hint promotion | `/actions`, plus explicit `/` and `/assets` | The new/linked Asset can affect Asset detail and Review; dynamic Asset pages rely on refresh/navigation rather than an explicit pattern invalidation here. |
| Asset create/edit/archive/restore | `/assets` and `/assets/[assetId]` page pattern | `/`, Search, linked Actions, and related-Asset candidate lists may also consume the state. |
| Asset Review | `/`, `/assets` | The affected Asset detail and linked-action context are not explicitly invalidated. |
| Asset evidence | `/assets` and profile pattern through ordinary mutation runner; capture-to-new-Asset additionally `/` | Evidence changes affect snapshot/search/review and may schedule background extraction. The exact profile must reconcile after upload/removal. |
| Saved Items | `/saved-items` | Promotion creates an Action; lifecycle and reminder changes can affect `/`, Search, Actions, and reminder deep links. |
| Person create/delete | `/people` | Search, dashboard People suggestions, Today, source-record resolutions, and any prefetched person detail may also be affected. |
| Person notes/memories/drafts | Exact person detail | Search, relationship snapshot, Review, dashboard/Eve context, and external Gmail state can also depend on the result. |
| Contact import | `/people` | Search and dashboard person suggestions also consume newly created People. |
| Integrations | `/account`; Discord delivery settings use `/account/discord` | Calendar suggestions/nudges, Gmail draft UI, Contact preview, and Discord callback/delivery state depend on capability changes. |
| Global Capture | `/saved-items`, `/actions`, `/people`, `/assets`, `/review`, `/today` | `/review` and `/today` are not live page routes. The actual Today/Review surface is `/`; capture can also affect a specific person or Asset detail. |

`router.refresh()` is currently doing important work beyond path invalidation: it re-renders the active server tree so server-derived tab counts and sibling lists can absorb additions. `useServerSyncedList` merges only previously unseen server ids; it intentionally preserves local removals and edits so a refresh does not resurrect a just-resolved row. Any Cache Components migration needs an explicit read-your-writes contract for both the returned mutation view and the refreshed server tree.

## Serialization, privacy, and consistency constraints

1. **Owner and caller are distinct concepts.** People and private review data are owner-scoped. Actions, Assets, Saved Items, follow-ups, evidence, and links can be caller-visible through household scope. Cache keys and tags must carry the identity and visibility dimensions used by the underlying query, not a generic “authenticated” key.
2. **A visible parent does not make every child visible.** Asset detail filters memories, evidence, related Actions, links, history, and review state per record. Caching the assembled profile under only `assetId` would cross privacy boundaries.
3. **Review state is owner-only and tentative.** It cannot share a cache with accepted domain records or with a household co-member's view. Acceptance must invalidate both the proposal collection and the destination record collection.
4. **Auth and provider tokens stay server-side.** Better Auth sessions come from request headers; OAuth tokens are encrypted and accessed through server integrations. Client-visible connection views are projections, not reusable provider credentials or authority.
5. **Client inputs are untrusted.** All server actions re-resolve admission and parse typed schemas. Owner ids passed into `AppShell`, local-storage keys, component props, route params, and search params are never sufficient authorization.
6. **Dates have domain semantics.** Follow-up/Action due dates are date-only local days; Saved Item reminders can be instants; Today is keyed to the owner's local date and time zone. Cache lifetimes and optimistic views must not normalize these into one timestamp model.
7. **RSC values are explicit projections.** Pages convert records into `*View` models, ISO/date strings, typed unions, maps reduced to arrays/objects, and bounded lists before crossing to clients. New cached functions should return the same serializable shapes or server-only records consumed before the client boundary.
8. **Fail-soft enrichment is intentional.** Review families, relationship snapshots, Gmail context, briefs, Calendar suggestions, and some provider reads degrade independently. Streaming boundaries must preserve useful successful content rather than turn optional enrichment failure into a full-page failure.
9. **Read-after-write spans routes.** The same mutation may affect Today rank, Review count, a domain list, a detail page, Search, reminders, and the shared shell. Path-only invalidation is currently incomplete for those consumers; introducing persistent caches without tags/keys would make the gaps durable.
10. **External work and background work are not the same as the initiating request.** OAuth callbacks, Gmail draft APIs, Contact preview/import, evidence extraction, reminders, and Eve can finish or fail on different timelines. The UI must distinguish accepted local intent, durable Tendnote state, provider confirmation, and later background enrichment.
