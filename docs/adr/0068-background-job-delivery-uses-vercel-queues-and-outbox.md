# Background Job Delivery Uses Vercel Queues and an Outbox

Tendnote lightweight async processors, starting with suggested-memory extraction and semantic embeddings, should keep product job state in Postgres while using Vercel Queues as the default production delivery mechanism. Queue delivery should use separate topic/consumer streams per processor family, with messages that carry `deliveryId`, `jobKind`, and `jobId` as pointers; consumers must reload the delivery intent and processor job from Postgres before processing, and duplicate, stale, or replayed messages should no-op through the processor's idempotent claim behavior.

Queue publishing belongs at the app/runtime edge, not inside the shared DB package. Shared packages own Postgres job enqueueing, claiming, processing, idempotency, retry state, and audit behavior; deployed web or agent runtime code composes "create the Postgres job, then publish the queue message" so Vercel transport and credentials do not leak into platform-neutral product logic.

Queue publication should be tracked through a narrow outbox-style `background_job_deliveries` table rather than hidden inside each processor table. The table tracks transport delivery only, not product outcomes, and should include `id`, `owner_user_id`, `job_kind`, `job_id`, `topic`, `status`, `attempts`, `last_error`, `next_attempt_at`, `created_at`, `updated_at`, and `published_at`. `job_kind` is an enum starting with `extraction` and `embedding`; `status` is `pending`, `published`, `publish_failed`, or `abandoned`; `topic` stores the concrete queue topic string used at publish time while code routes through a typed topic map keyed by `job_kind`.

Source-record capture and other durable user mutations must not fail solely because queue publication fails. The domain record and Postgres-owned job should commit first, delivery intent publication should happen after commit, and publish failures should leave inspectable, recoverable delivery rows. Mark delivery `published` immediately after Vercel accepts `send()`; do not use delivery status to mean the consumer received the message or that extraction/embedding completed.

Postgres remains the primary business retry and recovery authority. Queue retries cover transient delivery or consumer crashes around a single attempt, while shared processors decide `pending`, `failed`, `skipped`, `completed`, `runAfter`, attempts, and audit metadata. Cron is appropriate for a bounded generic recovery dispatcher that republishes undelivered intents and calls processor-specific backfill functions, but it should not become the normal production processing loop.

This is not a generic domain event bus or user-facing queue. Delivery visibility should stay backend-only in Phase 1 through schema state, structured logs, tests, and targeted recovery/inspection commands. Queue consumers should ship with conservative per-topic rate and concurrency defaults and reserve a small rate-control boundary such as `rateLimitKey` or `costCategory` so Phase 2B can apply shared Redis-backed budgets later without refactoring the delivery foundation.

Normal verification should stay local and deterministic. Tests should use fake queue adapters/messages to cover delivery lifecycle, payload validation, duplicate or stale messages, publisher behavior, consumer behavior, and recovery/backfill. Live Vercel Queue smoke tests may exist behind explicit credentials for deployment validation, but they must not be required for ordinary local or CI verification.
