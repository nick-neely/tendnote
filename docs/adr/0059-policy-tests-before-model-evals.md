# Policy Tests And Eve Evals Have Separate Jobs

Deterministic policy tests should live near the product logic they protect: domain rules in `packages/domain`, owner-scoped reads and writes in `packages/db`, integration adapters under their integration seams, and UI parsing/rendering in the relevant web modules. They should cover rules such as restricted content being excluded from proactive retrieval, dismissed memories being ignored, suggested memories not being stated as facts, pending source records not feeding normal contexts, duplicate names requiring disambiguation, approval gates, provider-scope boundaries, and memory writes requiring source records.

Eve evals are a separate agent-behavior surface, not a substitute folder for ordinary unit tests. They should run through Eve's real session protocol with `.eval.ts` cases, assertions, optional judge-backed scoring, targets, reporters, and strict CI output so Tendnote can evaluate tool choice, instruction and skill quality, refusal behavior, source grounding, approval behavior, and model suitability. Existing Vitest-style files under `apps/agent/evals` should move closer to the logic they test first; after that relocation, `apps/agent/evals` should be reserved for Eve-native evals only. Normal CI should block on fast deterministic Eve evals, while judge-backed and model-comparison runs stay explicit and credential-gated to avoid routine LLM cost, latency, and provider flake.
