# Semantic Retrieval Embeds Selected Context

Phase 1D pgvector semantic retrieval should come after relational retrieval, context snapshots, and full-text search are working. Embeddings should be generated for approved memories by default, and may be generated for active, person-linked, non-restricted source records only when they are retained/minimized user-created notes or interaction summaries. Generated context snapshots, suggested memories, dismissed records, archived records, personless pending source records, raw provider data, raw message logs, and restricted content should not be embedded by default.

Embeddings are another representation of the underlying content, not harmless metadata. Every embedding row must inherit the same access controls, sensitivity rules, visibility filters, and retention posture as its source item, and raw email bodies, raw message logs, dismissed memories, archived sensitive records, and high-risk sensitive notes should not be embedded by default.

Phase 1D should expose semantic retrieval to Eve through a distinct `search_semantic_context` tool backed by a shared owner-scoped query. It should return compact typed references with similarity, trust level, sensitivity, person metadata, snippets or embedded text, and source references; it should not return generated answers, full profiles, or context snapshot prose. Keeping this separate from `search_relationship_context` preserves the distinction between exact recall and fuzzy context-finding.

Phase 1D should not add a standalone semantic search page. The product surface should be Eve-first, with shared query/tool coverage and assistant result rendering as needed; a dedicated UI can wait for real usage evidence.

The embedding table should be `relationship_context_embeddings`, a generic relationship-context embedding table rather than `memory_embeddings`. It should carry owner, person, record kind, record id, model/version, embedded text, content fingerprint, trust level, sensitivity, and timestamps so semantic retrieval can cover both approved memories and selected source-record summaries without creating parallel embedding paths or implying every semantic match is a confirmed memory.

Embedding generation should be asynchronous and Postgres-owned, following the extraction-job pattern rather than blocking capture or review mutations on an embedding API call. Mutations should enqueue or stale-mark embedding work; workers, cron, or future queue delivery should carry job ids and call shared processing code while Postgres owns status, attempts, idempotency, backoff, errors, and completion. Semantic reads should fail open when embeddings are missing, stale, or still processing.

Phase 1D should keep only current embedding rows, not embedding history. One row per owner, source record or memory, embedding model, and embedding version is enough for retrieval; `content_fingerprint` should drive staleness and in-place replacement when the source text or embedding configuration changes. Historical facts, edits, and review actions remain owned by source records, memories, and audit logs rather than by embedding history.

`embedded_text` should be a deterministic minimized projection, not a raw dump of the source record. Approved memories may embed their approved content; source records should embed only retained/minimized fields such as interaction type, retained content, and resolved person display name when allowed. Raw provider payloads, unresolved mentions as facts, generated snapshot prose, and hidden restricted context should not be copied into embedding text.

Embedding generation should sit behind a replaceable adapter. The stored contract is the embedding vector plus `embedding_model`, `embedding_version`, and enough dimension/index compatibility metadata for safe reads; the provider or exact model name should not become a domain concept or hard-coded product assumption.

Phase 1D completion should be proven with deterministic fake-vector tests, not live embedding API calls. Tests should cover policy filtering, enqueueing, staleness detection, ranking, compact result shape, fail-open behavior, and Eve tool use. A real-provider smoke test can exist behind explicit credentials, but normal verification should not depend on network or provider availability.

Phase 1D ranking should be similarity-first after hard policy filters. Recency and importance may be light deterministic tie-breakers, but they should not overpower semantic match strength or turn semantic retrieval into recommendation ranking.

Eve may use semantic retrieval in Phase 1D to find grounded context for broad themes such as gift ideas, career updates, or stressful life events, but it should not treat those matches as proactive "who should I check in with" recommendations. Phase 1E.25's relationship agenda read model owns proactive cross-person ranking by combining deterministic signals such as due follow-ups, birthdays, review items, recent context, and later semantic candidates.
